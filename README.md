# Сервис контроля строительных площадок

Определяет по снимкам с камер, соответствует ли ход работ календарному плану, и
формирует вывод «соответствие» либо «отставание» с указанием причины.

Задача №7 конкурса ЛЦТ-2026, Департамент градостроительной политики Москвы.

## Как это работает

1. Снимок привязывается к дню календарного плана — на каждую дату демо-проекта
   `EDU-DEMO-001` приходится ровно одна активная работа.
2. Техника на кадре определяется двумя источниками: дообученным детектором RT-DETR
   для классов, которые он знает, и визуально-языковой моделью для остальных
   (башенный кран, бетононасос, автовышка, асфальтоукладчик, катки).
3. Найденное сверяется с правилами вида работ из `config/equipment_rules_v3.json`:
   признак работ, комплект техники, сопутствующая техника.
4. По накопленным продуктивным суткам считается темп этапа и прогноз отставания.

Каждая находка несёт источник признака: `detector` подтверждается рамкой на снимке,
`vlm` — текстовым обоснованием модели. Это сохраняет проверяемость вывода.

## Запуск

Нужны Python 3.12 и ключ мультимодальной модели.

```bash
poetry install
cp env_example .env          # вписать DEEPSEEK_API_KEY
poetry run python scripts/build_demo_stand.py    # собрать демонстрационный отчёт
poetry run uvicorn main:app --app-dir src --host 0.0.0.0 --port 8090
```

Сервис поднимется на `http://<адрес>:8090`.

| Страница | Что делает |
| --- | --- |
| `/` | демонстрация, загрузка своих данных, список прогонов |
| `/demo` | готовый разбор семи этапов, открывается мгновенно из кеша |
| `/runs/{id}` | прогресс разбора и итоги по этапам |
| `/cameras` | камеры площадки онлайн, архив съёмки, съёмка по кнопке |
| `/safety` | лента охраны труда: отметки моделей с кадром-доказательством |
| `/ingest` | что пришло с камер и запуск разбора по снятому |
| `/docs` | схема HTTP-API |

### Свои данные

На главной странице прикладываются **календарный план** таблицей и **снимки с камер**.

План — Excel или CSV с колонками «вид работ», «дата начала», «дата окончания».
Колонки ищутся по заголовку, порядок не важен; даты принимаются и в российской
записи, и в ISO. Сведений о технике в плане не нужно: правила задаёт сервис.

Снимки привязываются к этапам по времени съёмки из метаданных. Если времени в
снимках нет или оно не попадает в периоды плана, снимки раскладываются по этапам
в порядке загрузки — способ привязки пишется в отчёт прогона.

Разбор идёт фоновой задачей: страница прогона показывает, сколько кадров разобрано,
и обновляется сама.

### Камеры и охрана труда

Контур наблюдения показывает камеру онлайн, хранит снятое, снимает кадр раз в заданное
число минут и отдаёт снимки основному сервису по HTTP.

Камер шесть. Три — **настоящие стройки**: их публичные трансляции открыты по HLS, и OpenCV
собран с FFmpeg, поэтому отдельный медиасервер для них не нужен. Ещё три —
**демонстрационные ролики**, собранные генератором сцен из репозитория `video-monitoring`:
своей съёмки в том репозитории нет, зато есть генератор и посекундная разметка, по которой
меряются пороги проверок.

| Камера | Что даёт |
| --- | --- |
| ЖК «Цветочный город», Мытищи | монолит, котлован, два башенных крана; детектор техники находит экскаватор и погрузчики |
| ЖК «Счастье», Казань: фасад | леса и сетка; детектор зданий даёт 0,95 и находит 132 ячейки фасада |
| ЖК «Счастье», Казань: площадка | обзор сверху: люди 15–25 пикселей, модели не находят ничего — так выглядит неудачно поставленная камера |

```bash
poetry run python materials/external/video-monitoring-master/docker/scene_gen.py \
    --out data/cameras/scenes                    # собрать ролики камер
poetry run python scripts/measure_safety_checks.py   # замерить пороги проверок
```

Камеры описываются в `config/cameras.json`, проверки охраны труда — в
`config/safety_checks.json`. Пороги в файле проверок измерены по разметке сцен, а не
выбраны на глаз, и вместе с числами замера видны на странице `/safety`.

Каска определяется моделью CLIP: кадр и текстовая фраза кладутся в одно пространство,
и признак решается сравнением фраз «за» и «против». Абсолютная близость у этой модели
ничего не значит — работает только сравнение. Исхода три: признак есть, признака нет
и «не ясно», когда сравнение не разделило формулировки.

**Отметка — повод посмотреть кадр, а не установленный факт.** На замере ловится 45 %
нарушений, три отметки из четырёх верные; подмножество уверенных отметок на том же
замере не ошиблось ни разу. Нарушение подтверждает человек.

## Условия и ограничения

- **Классы техники** заданы обученной моделью RT-DETR: 17 классов, перечень и
  качество по каждому — в `models/facade/README.md` и `PROGRESS.md`. Классы
  `Roller` и `Trailer` в правилах не используются: на обучении они дали
  негодное качество.
- **Логика сопоставления** настроена на семь видов работ демонстрационного
  проекта. Этап загруженного плана связывается с ними по названию; если совпадения
  нет, этап остаётся без правил и в разбор не идёт.
- **Зонирование площадки не реализовано.** Определение «техника не в той зоне»
  требует разметки зон на кадре, которой в данных нет. Принято как допущение.
- **Перспективная трансформация фасада не воспроизводится:** у авторов моделей
  она берёт четыре точки из калибровки камеры. Область здания задаётся разметкой
  `config/camera_markup.json`, а при её отсутствии ищется детектором.
- **Фасадные веса** лежат вне репозитория: каталог `models/` не версионируется.
- **Живые камеры читаются по HLS.** RTSP открывается тем же вызовом OpenCV, но с настоящим
  регистратором контур не проверялся — такого под рукой нет.
- **Живой просмотр отдаётся кадрами JPEG** шириной 900 и не чаще пяти кадров в секунду.
  Без этих двух ограничений один зритель камеры 1920×1080 съедал по сорок мегабайт в секунду.
- **Трансляции чужие.** Они публичные и взяты как есть; для показа жюри этого достаточно,
  для эксплуатации нужна договорённость с владельцем камеры.
- **Непрерывной записи нет.** Круглосуточный архив — работа медиасервера; хранятся кадры
  по расписанию и короткий отрезок вокруг события.
- **Демонстрационные камеры рисованные.** Детектор техники обучен на фотографиях и на
  такой сцене находок не даёт: путь «камера → основной сервис» на них проверяется целиком,
  а находки по технике — нет. Проверка охраны труда на них работает.
- **Пороги проверок измерены на рисованных сценах.** На настоящих кадрах модель отвечает
  на тех же порогах в основном «не ясно»; для настоящих камер пороги надо мерить заново.


## Демонстрационный режим

Полный план проекта растянут на 294 дня, снимков на такой срок нет. Для показа
семь этапов на 294 дня — `config/calendar_plan_new.json`, 26 контрольных дат
с 2026-10-05. Переключается настройкой `USE_DEMO_PLAN`.

```bash
# разобрать все снимки моделями и сохранить результат в кеш (занимает минуты)
poetry run python scripts/run_demo_v2.py

# показать вердикты по восьми дням — читает кеш, модели не вызывает
poetry run python scripts/run_demo_v2.py --cached
```

Кеш лежит в `data/cache/demo_observations.json`. Такой порядок нужен, чтобы на
защите сервис отвечал мгновенно, а не ждал ответа модели по полминуты на кадр.
